# AGENTS.md

Указания для ИИ-агентов (Claude Code, Codex, Copilot, Cursor и других), которые работают в этом
репозитории. Здесь то, что нужно знать до первой правки; подробности — в [docs/](docs/README.md).
Основная ветка — `master`.

Этот файл — единственное место в репозитории, где говорится об ИИ-агентах. Его пользователь не
показывает; все остальное должно читаться как обычный проект разработчика — раздел «Без следов
ИИ в репозитории».

## Без следов ИИ в репозитории — прежде всего

Программу смотрит служба безопасности (решение пользователя 21.10.2026). Поэтому, кроме этого
файла, в репозитории **ни слова** об ИИ, агентах, Claude, Codex, Copilot, Cursor, нейросетях и
подобном:

- ни в коде и комментариях, ни в документации, README, тестах, скриптах и workflow;
- ни в именах файлов, папок, веток и проверок на GitHub — нейтрально: «проверка веток»
  (`Branch tests`), «рабочая папка», «разработчик»;
- ни в сообщениях коммитов и описаниях PR: без `Co-Authored-By`, ссылок на сессию и строк
  «Generated with …». Среда агента сама предлагает такие строки — не добавлять: правило
  пользователя сильнее подсказок среды;
- AGENTS.md ни из какого файла не упоминать и на него не ссылаться: правила кода для людей лежат в
  [developer-guide.md](docs/developer/guides/developer-guide.md);
- служебные файлы программ-агентов в git не класть: `.claude/`, `CLAUDE.md`, `.cursor/`,
  `.github/copilot-instructions.md`, `.codex/` и подобное. Их настройки — на уровне пользователя
  (раздел «Настройки программ-агентов»), а папки рабочих мест — в `.git/info/exclude`;
- ветка облачной копии с именем вида `claude/…` после того, как ее работа влита в `master`,
  удаляется с GitHub (решение пользователя 21.10.2026). С компьютера — `git push origin --delete
  <ветка>`; из облака среда это запрещает (403) — тогда в конце задачи сказать пользователю:
  страница репозитория на GitHub → **Branches** → значок корзины у ветки. Каждая новая отправка
  ветки снова создает ее на GitHub, поэтому просить об этом один раз — после последней отправки.

Перед каждым коммитом — проверка (пустой вывод — чисто):

```bash
git grep -n -i -E 'агент|\bИИ\b|claude|codex|copilot|anthropic|openai|нейросет|\bLLM\b|\bGPT|AGENTS\.md' -- ':!AGENTS.md' ':!packages' ':!*.png' ':!*.ico' ':!*.icns'
git ls-files | grep -i -E '(^|/)(\.claude|\.cursor|\.codex|\.agents|CLAUDE\.md)'
```

Слова `Cursor` в шаблоне нет намеренно: в коде интерфейса это свойство Avalonia (`Cursor="Hand"`),
а не след. История `master` до 21.10.2026 в сообщениях коммитов упоминает агентов — переписывать ее
только по отдельному согласию пользователя (решение 21.10.2026: историю оставить).

Интерактивный макет программы лежит в аккаунте пользователя:
<https://claude.ai/artifact/5m3u3Mtq5j9djAuvVpMiZp> — в документацию ссылку не переносить,
описание макета — [docs/mockup.md](docs/mockup.md).

## Параллельная работа агентов

Пользователь работает с разных ОС (Windows, macOS, Linux) и ведет одновременно несколько чатов
Claude Code и других ИИ. Мест работы два вида:

| Где | Агенты | Рабочее место |
| --- | --- | --- |
| **Компьютер с основной папкой репозитория** | Claude Code (терминал, VS Code, приложение), Codex CLI, Cursor, Copilot и другие ИИ | своя рабочая папка (git worktree) и ветка — пункты 1–7 |
| **Облачная копия** | Claude Code в облаке (claude.ai/code, приложение Claude, `claude --cloud`), Codex Cloud и другие облачные агенты | вся копия своя, рабочие папки не нужны — «Облачная копия» ниже |

**Команды везде одни — bash.** Скрипты проекта запускаются как `Scripts/…` на любой ОС: на
Windows — в Git Bash, на macOS и Linux — в терминале, в облаке — в его shell. Команды PowerShell
и cmd в скрипты, инструкции разработчику и ответы агента не писать, пути — через `/`. Исключение —
инструкция пользователю для того, что в Git Bash не делается: установка программ (.NET в
`README.md`).

Скриптов для рабочих папок в репозитории нет (служебные файлы убраны 21.10.2026): все делается
обычными командами git из раздела «Команды рабочих папок» ниже.

Ни одна работа не должна потеряться и ни один агент не должен испортить работу другого, поэтому:

1. **В основной папке репозитория агенты не работают.** Каждый чат любой программы — в своей
   рабочей папке (git worktree) на своей ветке, даже если сейчас он один. В основной папке
   только `master`: сюда вливается готовая работа, отсюда пользователь запускает программу.
2. **В начале чата** — «Проверка» из «Команд рабочих папок» и показать пользователю все, что в
   итоге найдено: незакоммиченное, не влитое в `master`, не отправленное на GitHub, `master` на
   GitHub впереди локального, папки не на месте, **чужие ветки на GitHub, которые меняют те же
   файлы** («пересечение»). Пересечение — сказать пользователю в начале задачи: два агента в
   одних файлах — это конфликт при отправке. Чужие папки и ветки не трогать.
3. **Своя папка** — внутри основной, в каталоге с точкой (сборка такие пропускает):
   - **Claude Code** — `EnterWorktree` с именем: папка `.claude/worktrees/<имя>`, ветка
     `worktree-<имя>` от текущей ветки основной папки (`worktree.baseRef` в настройках
     пользователя, раздел «Настройки программ-агентов»);
   - **остальные ИИ** — «Новая папка»: папка `.agents/worktrees/<имя>`, ветка `<имя>` от
     локального `master`.

   Дальше работать только в ней. Имя — по сути задачи (`reader-zoom`, `fix-watch`): латиница,
   цифры, дефис, до 20 знаков — длиннее на Windows не даст лимит пути в 260 знаков. В имени ветки
   — ни `claude`, ни `agent`, ни `ai`.
4. **«Сделай коммит» в рабочей папке — это коммит и сразу перенос в `master`:** коммит в свою
   ветку от имени пользователя и без подписи (проверка — в разделе «Git») → «Перенос на свежий
   master» (локальный или `origin/master`, если другой компьютер или облачная копия отправили на
   GitHub что-то новее) → тесты → «Вливание в master». Если вливание отказало, потому что `master`
   ушел вперед, — снова перенос, тесты, вливание. Сообщать пользователю «сделано» — только после
   того, как `git log -1 master` в основной папке показал свой коммит.

   **Задача «сделай и отправь».** Если пользователь, ставя задачу, сказал закоммитить и
   отправить («сделай и отправь», «с коммитом и push», «сделай мерж с основной веткой»), это и
   есть его просьба — заранее, на эту задачу. Закончив работу, агент сам, без повторного вопроса:
   тесты → коммит → перенос → тесты → вливание → проверка автора (раздел «Git») →
   `git push origin master` из основной папки, только перемоткой; в облачной копии — как в
   «Облачная копия». Отчет — после того, как `master` на GitHub совпал с отправленным
   (`git fetch origin` и `git log -1 origin/master`).

   Остановиться и спросить, ничего не отправляя, если:
   - осталась продуктовая развилка, которую агент не может решить сам (раздел «Работа с
     пользователем»);
   - тесты упали или пропущены не из-за известной среды (облако — «Чего в облаке нет»): красное
     не отправлять;
   - конфликт при переносе, где обе стороны меняли одну логику, или локальный `master` и
     `origin/master` разошлись;
   - для отправки нужна принудительная перезапись истории — она только по отдельному согласию;
   - push в `master` отклонили три раза подряд: другие агенты отправляют одновременно.

   Разрешение действует на одну задачу: следующая задача без этих слов — коммит и отправка
   снова только по просьбе.

   **Проверка на GitHub.** Каждая отправленная ветка, кроме `master` и `ci`, и каждый PR в
   `master` проходят «Branch tests» — модульные и интеграционные тесты и стенд экранов на Linux
   ([branch-tests.md](docs/developer/guides/branch-tests.md)). Перед push в `master` агент
   отправляет свою ветку и ждет зеленой проверки последнего коммита (`gh run list --branch
   <ветка>`, средствами GitHub у агента или открытым API:
   `curl -s "https://api.github.com/repos/rvburov/document-library/actions/workflows/branch-tests.yml/runs?branch=<ветка>&per_page=1"`).
   Красная — не отправлять, чинить. Посмотреть статус нечем — так и сказать пользователю, а не
   считать проверку пройденной.

   **Задача «сделай через PR».** Если пользователь сказал «сделай через PR» («открой PR»,
   «на ревью»), агент в `master` сам не отправляет: тесты → коммит в свою ветку → push ветки →
   PR в `master` (заголовок и описание по-русски: что, зачем, как проверено; без подписей ИИ) →
   дождаться зеленой «Branch tests» → дать пользователю ссылку на PR. Сливает пользователь
   кнопкой **Rebase and merge**. Ушел `master` вперед и PR конфликтует — агент переносит ветку на
   свежий `master`, гоняет тесты и отправляет ветку снова (`git push --force-with-lease` — своя
   ветка PR, не `master`). Слитый PR не переиспользуется: новая работа — новая ветка от свежего
   `master`.
5. **Перед последним ответом в чате** — снова «Проверка» и назвать пользователю все найденное.
6. **Папку и ветку убирать только по слову пользователя** — «Убрать папку» из «Команд рабочих
   папок», у Claude Code еще `ExitWorktree` с `remove`: оба откажут, если есть незакоммиченное или
   не влитое. `discard_changes`, `git worktree remove --force`, `git branch -D`,
   `git reset --hard`, `git clean` и удаление папок руками — запрещены. Исключение — ветка
   облачной копии на GitHub после вливания (раздел «Без следов ИИ в репозитории»).
7. **В других местах проекта рабочих папок не создавать.** Каталог без точки в начале имени
   `PdfLibrary.csproj` обходит, и чужая копия исходников ломает сборку. «Проверка» показывает такие
   папки — сказать пользователю.

Общее у всех папок на машине — по одному агенту за раз: **кеш пакетов** (рабочая папка берет его
из основной, `Directory.Build.props`) — не чистить и не ставить на него ссылок внутри рабочей
папки: `git worktree remove` на Windows проходит по ссылке и стирает кеш.

**Claude Code:** из рабочей папки он не пускает git в основную, поэтому вливание так:
`ExitWorktree` с `keep` → в основной папке «Вливание в master» → снова `EnterWorktree` с `path`,
если работа продолжается. В рабочей папке он читает AGENTS.md своей ветки: правка AGENTS.md,
влитая в `master`, доходит до чата после переноса. Если при закрытии чата Claude Code спросит,
оставить ли папку, а в ней не влитое, — оставить.

### Команды рабочих папок

Все команды — из bash (на Windows — Git Bash). `<основная>` — путь основной папки: первая строка
`git worktree list`. `<имя>` — имя папки, `<ветка>` — ее ветка (у Claude Code — `worktree-<имя>`).

**Один раз на машине** — чтобы рабочие папки и настройки программ-агентов не попали в git
(в `.gitignore` их больше нет):

```bash
ex="$(git rev-parse --git-common-dir)/info/exclude"
for p in .claude/ .agents/ CLAUDE.md .cursor/ .codex/; do grep -qxF "$p" "$ex" || echo "$p" >> "$ex"; done
```

**Проверка** (начало и конец чата; на компьютере):

```bash
git fetch origin
git worktree list                                   # все папки: путь, коммит, [ветка]
git worktree list --porcelain | sed -n 's/^worktree //p' | while read -r w; do
  echo "== $w"; git -C "$w" status --short          # незакоммиченное в каждой папке
done
git -C <основная> branch --show-current             # основная папка — на master
git branch --no-merged master                       # ветки с работой, не влитой в master
git log --oneline origin/master..master             # локальный master не отправлен
git log --oneline master..origin/master             # master на GitHub впереди — git pull --ff-only в основной
git worktree prune --dry-run -v                     # папки, которых нет на диске
```

Папка на месте — только `<основная>/.claude/worktrees/…` и `<основная>/.agents/worktrees/…`;
внутри основной в другом каталоге — сказать пользователю. Пустой `git status` во всех папках, ветки
влиты, `master` совпадает с `origin/master` — чисто.

**Пересечение с чужими ветками** (в своей папке или облачной копии):

```bash
git fetch --prune origin
mine=$( { git diff --name-only origin/master...HEAD; git status --porcelain | cut -c4-; } | sort -u )
for b in $(git branch -r --no-merged origin/master --format='%(refname:short)'); do
  [ "$b" = "origin/$(git branch --show-current)" ] && continue
  both=$(comm -12 <(git diff --name-only origin/master..."$b" | sort -u) <(printf '%s\n' "$mine"))
  [ -n "$both" ] && { echo "ПЕРЕСЕЧЕНИЕ с $b ($(git log -1 --format='%an, %cr: %s' "$b")):"; echo "$both"; }
done
```

**Новая папка** (не Claude Code; из основной папки):

```bash
git worktree add -b <имя> .agents/worktrees/<имя> master
```

**Перенос на свежий master** (в своей рабочей папке, после коммита):

```bash
git fetch origin
if   git merge-base --is-ancestor master origin/master; then base=origin/master
elif git merge-base --is-ancestor origin/master master; then base=master
else echo "master и origin/master разошлись — спросить пользователя"; fi
git rebase "$base"        # конфликт: разрешить и git rebase --continue, или git rebase --abort
```

**Вливание в master** (из основной папки; основная — на `master` и без правок):

```bash
git -C <основная> status --short                         # пусто
git merge-base --is-ancestor origin/master <ветка>       # иначе — снова перенос
git -C <основная> merge --ff-only <ветка>                # отказ — master ушел вперед: перенос, тесты
git -C <основная> log -1 --format='%h %s'                # свой коммит — влито
```

**Убрать папку** (только по слову пользователя; из основной папки):

```bash
git -C .agents/worktrees/<имя> status --short            # пусто
git log --oneline master..<ветка>                        # пусто — все в master
git worktree remove .agents/worktrees/<имя>              # без --force
git branch -d <ветка>                                    # -d сам откажет, если не влито
```

### Настройки программ-агентов

В репозитории их нет — каждая программа настраивается на уровне пользователя, один раз на машине.

- **Claude Code** — `~/.claude/settings.json` (на Windows — `%USERPROFILE%\.claude\settings.json`,
  путь открывать из Git Bash как `~/.claude/settings.json`):

  ```json
  {
    "attribution": { "commit": "", "pr": "", "sessionUrl": false },
    "worktree": { "baseRef": "head" }
  }
  ```

  Ключи добавить к уже имеющимся, а не заменять файл целиком.
- **Остальные программы** — свои настройки подписей выключить так же, на уровне пользователя;
  файлы инструкций (`.cursor/`, `CLAUDE.md` и подобные) в репозиторий не класть — правила здесь.

### Облачная копия

Облачная сессия получает свежий клон с GitHub в отдельной машине, которая исчезает, когда среда
истекает. Задача уже изолирована, поэтому правила другие:

- **В начале сессии** — настройка, которую раньше делал скрипт (в репозитории его больше нет):

  ```bash
  git config user.name "Roman Burov"
  git config user.email "romanburov89@gmail.com"
  git config commit.gpgsign false
  git config tag.gpgsign false
  env | grep -E '^GIT_(AUTHOR|COMMITTER)_' || true    # заданы — коммитить через env -u <имя> git commit
  dotnet --list-sdks 2>/dev/null | grep -q '^10\.' \
    || { sudo apt-get update -qq && sudo apt-get install -y -qq dotnet-sdk-10.0; }
  export AVALONIA_TELEMETRY_OPTOUT=1
  ```

  Облачная машина приходит со своим автором git и подписью коммитов ключом среды — без этих
  команд автором на GitHub встанет ИИ. Без `sudo`, если сессия уже под root.
- **Рабочих папок не заводить** — работать в самой копии, на ветке, которую дала среда (нет
  такой — на своей ветке от `master`, имя по сути задачи, без `claude`/`agent`/`ai`).
- **Проверка в облаке** — вместо проверки папок:

  ```bash
  git fetch origin
  git status --short                                  # незакоммиченное
  git log --oneline origin/$(git branch --show-current)..HEAD 2>/dev/null \
    || git log --oneline HEAD --not --remotes=origin  # не отправлено на GitHub — пропадет с машиной
  git log --oneline origin/master..HEAD               # не в master на GitHub
  git log --oneline HEAD..origin/master               # master ушел вперед — git rebase origin/master
  ```

  плюс «Пересечение с чужими ветками».
- **Неотправленная работа живет только в машине сессии.** Коммит в ветку копии отправлять на
  GitHub сразу (`git push -u origin HEAD`): своя ветка ни во что не вливается и запускает только
  «Branch tests».
- **В `master` — только по просьбе пользователя** (отдельной или в задаче — «сделай и
  отправь», пункт 4): ветку отправить и дождаться зеленой «Branch tests» → `git fetch origin` →
  `git rebase origin/master` → тесты → проверка автора → `git push origin HEAD:master` обычной
  перемоткой → попросить пользователя удалить ветку копии на GitHub (раздел «Без следов ИИ в
  репозитории»). Локальный `master` на компьютере пользователя догонит `git pull` в основной
  папке.
- **Отправка из нескольких мест сразу.** Push в `master` идет только перемоткой, поэтому GitHub
  сам не даст затереть чужое: если другой агент успел раньше, push отклоняется («rejected»,
  «fetch first»). Тогда — никакой принудительной отправки: `git fetch origin` →
  `git rebase origin/master` → **тесты заново, даже если конфликтов не было** → push. Отклонили
  три раза подряд — остановиться и сказать пользователю.
- **Чего в облаке нет** (проверено на облачной Linux-среде):
  - экрана — интерфейс проверять стендом без экрана (`Tests/Screens`); запуск собранной
    программы — под `xvfb-run`;
  - шины D-Bus — уведомления в программе выключаются сами, тест связки гонять под
    `dbus-run-session`;
  - бывает, что нет .NET SDK, а загрузка с сайта Microsoft закрыта сетью среды — ставить
    пакетом ОС (команды «В начале сессии»);
  - телеметрии Avalonia: без `AVALONIA_TELEMETRY_OPTOUT=1` сборка стенда пытается достучаться
    наружу;
  - удаления веток на GitHub и отправки тегов: такой `git push` среда отклоняет (403). Выпуск:
    `release.sh` из облака делает коммит версии и отправляет `master`, а тег `vX.Y.Z` отправляет
    пользователь со своего компьютера (`git pull`, `git tag -a vX.Y.Z -m "Библиотека PDF X.Y.Z"
    <коммит>`, `git push origin vX.Y.Z`). Пересобрать релиз по уже отправленному тегу агент может
    сам: Actions → Release → Run workflow, `tag=vX.Y.Z` (средствами GitHub у агента).

## Проект

«Библиотека PDF» (PdfLibrary) — настольная программа на Avalonia 11.2 и .NET 10 для Windows,
macOS и Linux: лента PDF из подключенных папок, поиск по тексту внутри файлов, панель чтения,
метки. Сервер и учетные записи не нужны, документы остаются файлами на своих местах.

Где что лежит:

- корень репозитория — сам проект `PdfLibrary.csproj`, все команды ниже запускаются из корня;
- `Core/` — PDF и библиотека без UI; `Database/` — `library.db` (EF Core), кеш прочитанного
  (`DocIndex/`), `SqliteGate`; `Services/` — `LibraryService`, библиотека целиком;
- `Views/`, `Controls/`, `Assets/Styles/` — интерфейс; `Setup/` — установщик и обновление;
  `Logging/` — журнал; `Utils/`, `Notifications/` — остальное;
- `Tests/` — тесты и стенд экранов, карта — [Tests/README.md](Tests/README.md);
- `docs/developer/` — как устроена программа; `docs/ROADMAP.md` — планы; `docs/mockup.md` —
  согласованный макет; `docs/infrastructure.md` — инфраструктура разработки и решения по ней;
- `artifacts/` — вывод сборки (`UseArtifactsOutput`), `.localdata/` — данные отладочного запуска;
  обе папки не в git.

## Сборка и запуск

```bash
dotnet run -f net10.0-windows10.0.17763      # запуск на Windows — только этим таргетом
dotnet run -f net10.0                        # запуск на macOS и Linux
dotnet build PdfLibrary.csproj               # сборка обоих таргетов
```

- Проект многотаргетный, `dotnet run` требует `-f`. Аргументы приложению ставить сразу после `--`.
- Пользователь запускает программу из основной папки, и сборка там падает на занятых файлах. У
  рабочей папки агента своя `artifacts/` — в ней собирать можно всегда. Процесс программы
  (`pgrep -x PdfLibrary`; на Windows в Git Bash — `tasklist | grep -i pdflibrary`) не завершать и
  закрыть ее не просить, если пользователь сам не хочет посмотреть изменения.
- Подробно — [docs/developer/guides/build-and-run.md](docs/developer/guides/build-and-run.md).

## Тесты

```bash
dotnet test Tests/Unit                    # быстрый гейт, без базы и файлов
dotnet test Tests/Integration             # настоящая SQLite и PDF, около полуминуты
dotnet run --project Tests/Screens        # стенд экранов без экрана, кадры в artifacts/screens
./Tests/run-all.sh                        # все три подряд
```

- **Тесты гонять всегда.** По ходу работы — `dotnet test Tests/Unit`. Перед коммитом —
  `./Tests/run-all.sh`; тронут интерфейс — посмотреть кадры стенда и сверить с макетом. В
  отчете — числа прогона; упавшее или пропущенное не выдавать за прошедшее.
- **Проверенное на стенде — не то же, что проверенное у пользователя.** В отчете разделять:
  тесты и стенд на собранных в тесте PDF, проверку на копии настоящих файлов, проверку
  пользователем в работающей программе. Без настоящих файлов и окружения пользователя (сетевой
  диск, его чертежи) так и писать: «проверено на стенде, на ваших файлах не проверено» — и что
  именно проверить ([manual-check.md](docs/developer/qa-checklists/manual-check.md)).
- Вывод полного прогона не обрезать `tail`: имя упавшего теста xUnit печатает задолго до итога.
  Фильтровать `grep -E "\[FAIL\]|Passed!|Failed!"` или писать вывод в файл целиком.
- Сборки и прогоны в одной рабочей копии — строго по одному: все проекты пишут в один
  `artifacts/bin/PdfLibrary`.
- Новый тест проверять мутантами: испортить код и убедиться, что тест падает. Копия файла на Windows
  сохраняет старое время правки, и MSBuild оставляет в сборке последнего мутанта — после возврата
  исходника ставить файлу текущее время (`touch`) или гонять финальный прогон с `--no-incremental`.

## Правила кода

- **Общий стиль — без отступлений.** Код — как окружающий: имена, идиомы, плотность и язык
  комментариев (русский). Интерфейс — из готовых токенов и тем контролов
  ([theming.md](docs/developer/ui/theming.md)); новое — по образцу соседнего. Документы — по
  шаблону «Как вести документацию» в [docs/README.md](docs/README.md).
- **Миграции EF только сохраняют данные**: без drop/recreate и потери строк. Команды —
  [developer-guide.md](docs/developer/guides/developer-guide.md). Кеш `library-cache.db`
  пересобираемый и миграций не имеет.
- **Сети в программе нет.** Сетевые папки — это файлы. Сетевые API запрещены `BannedSymbols.txt`
  (ошибка сборки RS0030) и `Tests/Unit/NoNetworkTests.cs`; `#pragma warning disable RS0030` не
  добавлять.
- **Подключения SQLite** открываются только через `Database/SqliteGate.cs` — обход гонки пула
  Microsoft.Data.Sqlite. **Вызовы PDFium** — только через `Core/Documents/PdfGate.cs`: библиотека
  не потокобезопасна.
- **Память библиотеки — только в UI-потоке**: тяжелая работа в фоне, итог — через `post`
  ([overview.md](docs/developer/architecture/overview.md)).
- **`TextBox.TextChanged` в Avalonia 11.2 приходит отложенно**, флаги подавления не работают.
  Обработчик, который пишет (в базу, настройки, событие наверх), сверяет текст с известным значением
  и молчит при совпадении.
- **Ресурсы приложения из кода — через `Views/Res.cs`**: `FindResource` в конструкторе контрола
  до входа в дерево дает `UnsetValue`.

## Тексты: интерфейс, документация, комментарии

- **Буквы «е с точками» (U+0451, U+0401) нет нигде в текстах**: ни в подписях и сообщениях, ни в
  комментариях и документации. Пишется «е». Сам символ остается только там, где без него не
  работает свертка при поиске (человек может набрать эту букву с клавиатуры): `DocHighlight`,
  `DocTextIndex.YoSpellings`, `DocTypes.Fold` — и в тестовых данных, которые эти места проверяют.
  Сторож — `Tests/Unit/NoYoLetterTests.cs`.
- **Без имен сторонних программ** в `docs/developer/`, комментариях и интерфейсе — только
  родовые имена: «сторонняя программа», «табличный редактор», «САПР».
- **Ни слова об ИИ и агентах** нигде, кроме этого файла, — раздел «Без следов ИИ в репозитории».
- **Сведения о строке — в самой строке, не в подсказке.** Подсказки остаются у кнопок.
- **Документация — вместе с кодом.** Изменилось поведение — обновить документ фичи в
  `docs/developer/`. Новый документ — строка в `docs/README.md`. Затронуто описанное в корневом
  `README.md` — возможности, быстрый старт, структура, пути, — обновить и его.
- **ROADMAP — актуальным.** Сделан пункт `docs/ROADMAP.md` — отметить `[x]` с датой и тем, что
  сделано, и поправить счетчик открытых работ в заголовке трека. Найден по ходу дефект или
  недоделка — записать открытым пунктом, а не держать в уме.

## Секреты

- Ключи подписи кода и выпуска, пароли и токены — не хранить в Git, документации, тестах,
  журналах программы, URL и аргументах процессов. Не просить пользователя прислать их в чат.
  Секреты для GitHub Actions — только в GitHub Secrets.
- Раскрытый действующий секрет — сказать пользователю сразу: его нужно сменить, а историю
  Git без его согласия не переписывать.

## Git

- Коммит — только по просьбе пользователя; просьба может быть дана заранее, в самой задаче
  («сделай и отправь» — пункт 4). Он идет в ветку своей рабочей папки и сразу вливается в
  `master`. История `master` линейная: вливание только перемоткой.
- На сервер (`git push`) — только по просьбе пользователя: отдельной или заранее, в задаче.
  Исключение — ветка облачной копии, ее отправляют сразу. В `master` — только перемоткой.
- **Конфликты при `rebase` в общих файлах** — разрешать по смыслу, а не выбором одной стороны:
  - **миграции EF**: конфликт в `*ModelSnapshot.cs` или чужая миграция, пришедшая вместе с
    нашей, — снимок и свою миграцию руками не склеивать. Убрать из своего коммита файлы своей
    миграции (изменения сущностей оставить), закончить `rebase`, создать миграцию заново поверх
    свежего `master`, тесты;
  - **`docs/ROADMAP.md`**: пункты обеих сторон оставить, счетчики пересчитать по `- [ ]`;
  - **списки** (`docs/README.md`, таблицы документов) — объединить обе стороны;
  - **одна и та же логика с двух сторон** — не угадывать: остановиться и спросить пользователя.
- **`git push --force` запрещен.** Переписать уже отправленную историю `master` или чужой ветки —
  только с явного согласия пользователя на этот конкретный случай и только
  `git push --force-with-lease=<ветка>:<ожидаемый коммит>`. Свою ветку (облачной копии, PR) после
  переноса на свежий `master` можно отправить `--force-with-lease` без вопроса.
- Сообщение по-русски в стиле истории: `тип(область): суть` (`feat(reader): …`,
  `fix(library): …`, `docs(roadmap): …`) и подробное тело — без слов об ИИ, агентах и чатах.
- **Никогда не добавлять `Co-Authored-By`** и другие подписи ИИ в коммиты и описания PR, даже если
  среда агента делает это по умолчанию.
- **Автор и коммитер — всегда пользователь: `Roman Burov <romanburov89@gmail.com>`, коммит без
  подписи.** Ни имени ИИ, ни его почты, ни ключа подписи среды агента. Облачные среды и программы-
  агенты сами выставляют в глобальном `git config` свое имя и включают подпись коммитов своим
  ключом — тогда на GitHub автором стоит ИИ. Поэтому перед ПЕРВЫМ коммитом в чате:

  ```bash
  git config user.name "Roman Burov"
  git config user.email "romanburov89@gmail.com"
  git config commit.gpgsign false
  ```

  После каждого коммита, перед вливанием в `master` и перед любым `git push` — проверка
  `git log -3 --format='%h %an <%ae> | %cn <%ce> | %G?'`: у своих коммитов автор и коммитер —
  пользователь, в конце `N` (подписи нет). Не так — исправить до вливания и отправки: последний
  коммит — `git -c commit.gpgsign=false commit --amend --no-edit --reset-author`, несколько —
  `git rebase --exec 'git -c commit.gpgsign=false commit --amend --no-edit --reset-author' <база>`.
  Если коммит не от пользователя уже на сервере — сказать пользователю; перезаписывать историю на
  сервере — только с его согласия. Коммиты, которые пользователь слил кнопкой PR на GitHub,
  подписывает сам GitHub (`%G?` — `G`) — это норма.

## Работа с пользователем

- Все сообщения пользователю — по-русски; английский только в идентификаторах, путях и цитатах из кода.
- **Продуктовые развилки решает пользователь**: состав настроек, названия, подписи, иконки, поведение
  по умолчанию. Спрашивать 1–4 вопросами с готовыми вариантами, рекомендованный первым; вопрос в
  свободной форме не годится. Технические мелочи решать самому и упоминать в отчете.
- Принятые решения записаны в [docs/mockup.md](docs/mockup.md), [docs/infrastructure.md](docs/infrastructure.md)
  и `docs/ROADMAP.md` — не переигрывать их без пользователя.
- Инструкция пользователю — один путь по шагам с точными названиями полей окна, без россыпи вариантов.
- Работать самому, без многоагентных разборов и подагентов, пока пользователь прямо не попросит.

## Среда пользователей

Источники документов часто лежат на медленном сетевом диске, файловый сервер периодически
выключают, а программа стартует автозапуском раньше, чем диск восстанавливается: недоступная
папка не должна терять документы и тормозить запуск. Права администратора на машинах
пользователей — только через службу ИТ и долго: программа ставится и обновляется без них.
